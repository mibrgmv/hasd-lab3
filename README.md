# Лабораторная 3: сжатие без потерь для формата из лабы 1

Формат **HBC2** – колоночный формат HBC1 из лабы 1 плюс свой компрессор (контекстное моделирование
+ арифметическое кодирование). Датасет Яндекс.Метрики `hits_v1` (ClickHouse), Go без сторонних библиотек.

|                |                                                   |
|----------------|---------------------------------------------------|
| Исходный TSV   | 7 784 МБ, 8 873 898 строк, 133 колонки            |
| HBC1 (лаба 1)  | 949.6 МБ                                          |
| xz над TSV     | 851.5 МБ                                          |
| xz над HBC1    | 521.8 МБ                                          |
| HBC2           | **462.0 МБ (5.93%, в 16.9 раза меньше)**          |
| Кодирование    | 9 мин 4 с (Apple M2, 8 ядер)                      |
| Декодирование  | 8 мин 18 с                                        |
| Проверка       | sha256 декодированного файла совпадает с исходным |

xz – настройки по умолчанию (пресет 6, все ядра).

## Запуск

```bash
mkdir -p data
curl -o data/hits_v1.tsv.xz https://clickhouse-datasets.s3.yandex.net/hits/tsv/hits_v1.tsv.xz
xz -dc data/hits_v1.tsv.xz > data/hits_v1.tsv

go build -o bin/hits ./cmd/hits
./bin/hits encode -o data/hits_v1.hbc2 data/hits_v1.tsv   # печатает таблицу по колонкам
```

Проверка, что датасет восстанавливается без изменений:

```bash
shasum -a 256 data/hits_v1.tsv
./bin/hits decode data/hits_v1.hbc2 | shasum -a 256
# оба раза: 4e9bc368ff3c139131dee42a63d68e6d8069641303b304c133540dc1e56c8e43
```

Сравнение с xz:

```bash
xz -c data/hits_v1.tsv | wc -c
```

Прочее:

```bash
go run ./cmd/profile data/hits_v1.tsv      # статистика по колонкам датасета
go run ./cmd/hypotheses data/hits_v1.tsv   # проверка гипотез о связях между колонками и строками
```

## Как устроено

```
"HBC2" | число строк | оглавление: имя, тип, размер блока каждой колонки | блоки колонок
блок колонки: заголовок (способ, параметры) | потоки: словарь, значения, длины серий
```

Колонки кодируются независимо, как в HBC1: `const`, `plain`, `delta`, `dict`, любой из них с RLE.
Отличия от HBC1:

- значения пишутся целыми байтами, а не битовой упаковкой – иначе компрессор не видит границ значений;
- словарь строк – текст построчно, в порядке первого появления значений;
- номер в словаре кодируется как расстояние до следующего нового значения: новое – 0, недавнее – маленькое число;
- каждый поток сжимается компрессором `internal/cm`, все потоки всех колонок параллельно.

Компрессор (по мотивам lpaq/PAQ) кодирует байт по битам. Вероятность бита дают модели по последним
0–4 и 6 байтам, модели по позиции в записи (числовые потоки) или по словам (текст) и match-модель;
их смешивает логистический mixer, бит записывает арифметический кодер. Декодер повторяет те же
предсказания, поэтому распаковка занимает столько же, сколько сжатие. Подробности – в отчёте.

## Структура

```
cmd/hits            encode / decode
cmd/profile         статистика по колонкам датасета
cmd/hypotheses      проверка гипотез о связях между колонками и строками
internal/cm         компрессор: модели, mixer, арифметический кодер
internal/codec      формат HBC2: выбор способа (intcol.go, bytescol.go), байтовые потоки (stream.go), сборка файла (file.go)
internal/tsv        нарезка TSV на строки и поля без копирования, параллельный обход колонок
internal/textval    разбор и печать чисел и дат (только каноничная запись)
internal/schema     схема hits_v1 (schema.txt)
reports/            profile.txt – статистика датасета; encode_v1.txt, encode_v2.txt – HBC1 по колонкам из лабы 1
```
